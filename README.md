# krateo-backstage-kog

Krateo controllers for the backends behind Backstage's plugin ecosystem, generated by
[`oasgen-provider`](https://github.com/krateo-platformops/oasgen-provider) from vendor OpenAPI
documents.

A Backstage plugin is two things: a **frontend** that renders panels, and a **backend integration**
that talks to some vendor API. This repository is the second half. The first half —  portal widgets —
lives in [`krateo-backstage-blueprint`](https://github.com/krateo-blueprints/krateo-backstage-blueprint).

## What belongs here

One `RestDefinition` per vendor API, following the established KOG pattern
(`github-provider-kog`, `krateo-keycloak-operator-kog`, the `openstack-*-operator-kog` family).
Each definition names the vendor's own OpenAPI document, the kinds to generate, and the verbs each
kind holds.

## What does NOT belong here

- **Backstage's own machinery.** The catalog, scaffolder, permissions and search plugins have no
  vendor API to wrap: their Krateo counterparts are a different mechanism entirely (CRs, Builders,
  Kubernetes RBAC, snowplow). There is nothing to generate.
- **GraphQL backends.** `oasgen-provider` takes an OpenAPI document as its only input, so New Relic
  (NerdGraph) and GitHub Discussions cannot have a generated controller. They are widgets-only, by
  construction rather than by omission.
- **Pure-frontend plugins.** Tech Radar needs one widget and no controller.

## Status

Nothing is generated yet, and that is deliberate. **Four of the highest-value targets cannot be
expressed by `oasgen-provider` today** — ArgoCD, Grafana, Argo Workflows and Harbor all publish
Swagger 2.0, which the parser rejects at ingest. See the tracking issue for the ordered list of
what `oasgen-provider` must implement first, each item with the API that needs it and the evidence.

The research behind that issue is in `docs/` — including, deliberately, a list of what could not be
verified.
